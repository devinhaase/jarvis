# Jarvis Android app

A native WebView shell around Jarvis's own web UI — connects to the one configured main
computer (local network first, then Tailscale VPN), wakes it via Wake-on-LAN if it's asleep,
and gets mic/OAuth/push working the way a bare WebView doesn't by default. See `task.md`'s
entries for the full tier-by-tier build writeup and every real bug hit along the way. This
file is the quick reference: what's here, one-time setup, troubleshooting.

## Files

| File | What it does |
|---|---|
| `app/src/main/java/com/dhaaselab/jarvis/MainActivity.kt` | The app itself — hosts the WebView, resolves which address to use, wires mic/popup/notification handling. |
| `ConnectionManager.kt` | Local → Wake-on-LAN retry → VPN fallback chain (Tiers 7/7a). |
| `ConnectionPrefs.kt` | Where "the main computer" is — editable from the in-app Settings screen, no rebuild needed. |
| `WakeOnLan.kt` | Sends the actual magic packet (Tier 7a). |
| `JarvisFirebaseMessagingService.kt` | Turns FCM messages into real Android notifications (Tier 10). |
| `FcmTokenStore.kt` | Holds this device's current FCM token between app launches. |
| `SettingsActivity.kt` | The in-app settings screen (computer name, local/VPN address). |
| `build_icons.py` | Regenerates the launcher icon PNGs from `../webapp/icon.svg`. Run manually, only when the icon changes. |

## First-time setup / rebuilding

```
cd android_app
./gradlew assembleDebug      # debug build, installable via adb install
./gradlew bundleRelease      # release .aab for Play Console (Tier 11 — needs signing config first)
```

Needs a JDK 17 and the Android SDK (`local.properties`' `sdk.dir`, or `ANDROID_HOME`) —
see `task.md`'s Tier 7 entry for exactly what was installed to build this the first time
(JDK, cmdline-tools, platform 34, build-tools, an emulator for testing) if setting this up
on a fresh machine.

## Tier 10 — turning push notifications on (Devin's own one-time setup)

This app's push notification code is fully built and gracefully does nothing until this is
done — no crash, no broken build, just no push. Google Firebase project creation is an
account-level action only you can do (same reasoning as Google Play Developer registration
in Tier 11 — not something this agent can do on your behalf). Concretely:

1. Go to the [Firebase console](https://console.firebase.google.com/), create a new project
   (any name).
2. Add an Android app to it, package name **exactly** `com.dhaaselab.jarvis`.
3. Download the `google-services.json` it gives you, place it at
   `android_app/app/google-services.json`. The next `./gradlew assembleDebug` picks it up
   automatically — nothing else to change in any build file.
4. In the Firebase console: Project Settings → Service Accounts → "Generate new private
   key". Save that JSON as `data/firebase-service-account.json` in the main project root
   (not `android_app/`) — this is what `push_notifications.py`'s `_send_fcm()` uses to
   authenticate to the FCM HTTP v1 API. Keep it out of git (already covered by
   `.gitignore`'s `data/` entry).
5. Rebuild and reinstall the app. First launch requests the notification permission
   (Android 13+) automatically.

Once both files exist, everything else — token registration, category-based channels,
deep-linking a tap to the right conversation — already works, reusing the exact same four
categories (approvals/alerts/briefing/messages) and quiet-hours logic the desktop/web push
notifications already have (`push_notifications.py`).

## Tier 11 — signing, release build, and what's left for the Play Console

**Already done, verified working:**
- A real upload-signing keystore (`jarvis-upload-key.jks` + `keystore.properties`, both
  gitignored — **back these up somewhere safe**, e.g. a password manager; losing both means
  losing the ability to publish updates under the same app identity unless Play App Signing
  is already enrolled, see below).
- `./gradlew bundleRelease` produces a genuinely signed `.aab`
  (`app/build/outputs/bundle/release/app-release.aab`) — verified with `jarsigner -verify`,
  not just "the build didn't fail."
- The adaptive icon (`ic_launcher_foreground.png` + a solid-color background layer per
  Android's own adaptive-icon format), generated by `build_icons.py` from the same source
  SVG the desktop app and web UI use, confirmed rendering correctly (properly masked into a
  circle) in a real launcher.
- `PLAY_STORE_LISTING.md` — the app title/description/Data safety answers/content rating
  guidance, ready to paste into the Play Console.
- A real, published privacy policy (required once mic/notifications are requested):
  https://claude.ai/code/artifact/5a16f698-7875-4197-bc99-38dfcf8c8748

**What's left, and has to be Devin's own action** (account/payment/device actions this
agent can't perform — see the project's own safety rules on prohibited actions):
1. Register a Google Play Developer account (one-time ~$25 fee + identity verification —
   confirm the current exact fee/steps in the Play Console at signup, Google updates these
   periodically).
2. Create the app listing in Play Console, choose **Internal testing** track (per the Part
   2 interview — no public review, installs only for accounts you add).
3. Upload `app-release.aab`, paste in `PLAY_STORE_LISTING.md`'s text, fill in the Data
   safety section from the table there, take a couple of real phone screenshots (the
   emulator ones from testing this build are a lower-res stand-in if needed).
4. Enroll in **Play App Signing** when prompted during the upload flow — Google then holds
   the real signing key, `jarvis-upload-key.jks` becomes just the upload key you keep
   (matches the spec's own "Google holds the app signing key, I keep the upload key").
5. Add your own Google account (or whichever accounts should get the internal testing
   build) to the testers list, and share the opt-in link it gives you.
6. Complete Tier 10's Firebase setup (see above) before or after this — independent of
   signing, but push notifications won't do anything until both are done.

## Part 3 — knowing when this app itself needs rebuilding

Same principle as the desktop app: any change under `webapp/` (dashboard, chat UI, prompts)
is served live from `server.py` and needs **zero** app update — this app just loads the page
fresh every launch, same as any browser. Nothing below applies to those changes.

This app only needs an actual rebuild + reinstall (and, once published, a real Play Console
release) when the native shell itself changes — `MainActivity.kt` or anything else under
`app/src/main/java/`.

To catch a stale native shell before it causes confusion, `MainActivity.checkNativeShellVersion()`
runs once per page load (from `WebViewClient.onPageFinished`, right after the FCM token
injection) — it hits `server.py`'s `GET /native-shell-version`, reads
`android_min_version_code`, and compares it against this build's own `BuildConfig.VERSION_CODE`
(exposed via `buildFeatures { buildConfig = true }` in `app/build.gradle.kts`). If the
server's minimum is higher, it injects a small banner into the loaded page
(`#jarvis-android-update-banner`, idempotent) reading "A new version of this app is ready in
Play Store internal testing." If they match, nothing is injected.

**When bumping the native shell in a way that matters**, bump `versionCode` (and `versionName`)
in `app/build.gradle.kts` and `ANDROID_MIN_VERSION_CODE` in `server.py` together, then
rebuild, re-sign, and push the new release to the Play Console's internal testing track —
that's what makes any install still running the old shell show the banner until it updates.

Live-verified both directions on the emulator: built and installed a debug APK at
`versionCode = 1`, temporarily bumped `server.py`'s `ANDROID_MIN_VERSION_CODE` to `2` and
restarted the server, force-stopped and relaunched the app, and confirmed via Chrome DevTools
Protocol (`adb forward` to the app's `webview_devtools_remote_<pid>` socket, then
`Runtime.evaluate` reading `#jarvis-android-update-banner`'s `innerText` — the same CDP
approach used to verify Tier 9's popup escape) that the banner text appeared exactly as
written above. Reverted `ANDROID_MIN_VERSION_CODE` back to `1`, restarted the server again,
force-stopped and relaunched the app fresh, and confirmed the banner element is absent
(`document.getElementById(...)` returns `null`) on a normal, up-to-date launch.

## Known, deliberate scope boundaries

- **Mic only works over the VPN connection, not the local/LAN one.** Real finding from
  building Tier 8: Android WebView only exposes `getUserMedia()` in a secure context
  (HTTPS, or literally `localhost`) — a plain `http://192.168.1.147:8765` LAN address
  doesn't qualify, same wall the desktop browser hit before this Android work even started.
  The VPN address is `https://ai.dhaaselab.com` specifically *because* it already has a
  real trusted cert (Caddy + DNS-01, see `caddy/Caddyfile`) — reusing existing
  infrastructure rather than building new. Everything else (chat, notifications) works
  fine over the local connection; this is scoped to the microphone only.
- **A live, separate finding, not related to this app's own code**: while verifying the
  above, `ai.dhaaselab.com` failed to resolve from this machine's own configured DNS
  resolver (192.168.1.1, the router) even though public resolvers (1.1.1.1, 8.8.8.8) return
  the correct answer immediately. Worth checking the router's DNS forwarder if the VPN path
  (and therefore mic-over-VPN) doesn't work — this is a home-network issue, not something in
  this app or the Caddy setup.
- **No dashboard view.** This app only ever loads the chat page (`/`), never the
  standalone `/dashboard` page the desktop/web clients have — a `dashboard`-targeted push
  notification (team/approval deep link) still opens straight into chat rather than
  pretending to go somewhere this app doesn't have a screen for.
- **Notification icon is a placeholder** (`android.R.drawable.ic_dialog_info`, a generic
  system icon) — a proper small monochrome status-bar icon (Play Store/Android notification
  design guidelines want a flat white silhouette, not the full-color app icon) is a Tier 11
  polish item, not done yet.

## Troubleshooting map

- **App can't reach the server** → check the local-address timeout isn't too aggressive,
  confirm the VPN domain is actually correct when off wifi (Tier 7).
- **App connects to the wrong device, or nothing at all** → the configured main-computer
  address in Settings is stale; re-check/edit it there.
- **Wake-on-LAN doesn't wake the machine** → confirm WOL is enabled on the main computer's
  NIC in BIOS/adapter power settings, and that it's only being attempted on the local
  network, not over VPN (by design — see `WakeOnLan.kt`'s own docstring).
- **No mic prompt at all** → `ensureMicPermission()` never ran, or ran after the WebView
  already tried. Check you're connected over the VPN address, not local (see the scope
  boundary above) — `NotFoundError`/silence on local is expected, not a bug.
- **Mic prompt granted but `getUserMedia` still fails** → check which address the app is
  actually connected through (Settings screen shows "Connected via"); local never works,
  VPN needs `ai.dhaaselab.com` to actually be resolving (see the DNS finding above).
- **Sign-in does nothing** → `onCreateWindow` not firing; confirm
  `setSupportMultipleWindows(true)`/`javaScriptCanOpenWindowsAutomatically` are still set in
  `configureWebView()`.
- **Notifications never arrive** → confirm both `google-services.json` and
  `data/firebase-service-account.json` exist (Tier 10 setup above); check the server log for
  `[push_notifications] FCM not configured yet` or a real send error.
- **Play Console rejects the listing** → usually a Data Safety mismatch or an overly
  specific description of capability (Tier 11).
